# Deletion confirmation

How DevMentor asks before it removes something that cannot be brought back. Built on the [confirmation dialog](?path=/docs/primitives-confirmation-dialog--docs) and used for removing an availability window.

## Purpose

A person never removes something by accident, and always knows what will happen to it.

## When to use

- Removing an availability window (E01-S02).
- Any removal that has no undo: later, a profile link or an invitation.

## When not to use

| Situation                                           | Use instead                                                               |
| --------------------------------------------------- | ------------------------------------------------------------------------- |
| Cancelling a booking, which has a refund outcome    | The cancellation dialog (E02), same structure with the outcome written in |
| Something that can be undone or added again at once | Do it, and say so next to the item. Do not confirm every action.          |
| An operator action that needs a reason              | The operator action pattern (E05)                                         |

## Dialog or direct action

**Undoable** means the person can restore it themselves from a place the toast names, with no money moved, nobody notified and nothing they typed lost. Undoable: do it directly (a button, then a toast after the server confirmed; no dialog, no Undo in the toast). Anything else: a confirmation dialog (the rules below).

| Removal                                   | Undoable | Why                                                                                    | Use                      |
| ----------------------------------------- | -------- | -------------------------------------------------------------------------------------- | ------------------------ |
| A mentor from favorites                   | Yes      | Saved again from the mentor's profile; nothing else happens                            | Button, toast            |
| A mentor from "recently viewed"           | Yes      | Opening the mentor's page lists them again; nothing else happens                       | Button, toast            |
| An availability window                    | No       | Mentees can no longer book it, and re-adding is a new window                           | Confirmation dialog      |
| A booking (cancel)                        | No       | Money and the other person are involved                                                | Cancel dialog            |
| An invitation (revoke)                    | No       | The invited person is affected and the link stops working                              | Operator action pattern  |

A past session cannot be hidden from the list at all (owner decision, 2026-10-28): history stays complete, so there is no hide action to confirm.

Worked example of the direct case: removing a mentor from favorites ([Favorites page](?path=/docs/design-system-favorites--docs)). The button reads "Remove from favorites", is `secondary` and `dense`, and the toast reads "Anna Kowalska removed from favorites" with "You can save this mentor again from their profile." The toast sentence names the place to restore from. The behavior is the `useItemRemoval` hook.

## Rules

| #   | Rule                                                                                                 | How it is built                                                                                      | Source               |
| --- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | -------------------- |
| 1   | The question names the object: "Remove Fri 13 Nov, 10:00 to 12:00?"                                  | `AlertDialogTitle` built from the item's own description.                                            | P10.1, WCAG 3.3.4    |
| 2   | The text says what happens, and what does not.                                                       | "Mentees can no longer book this window. A session that is already booked is not cancelled by this." | P10.1, E01 spec      |
| 3   | Cancel is easy to find: it comes first and takes initial focus, so Enter never confirms by accident. | `AlertDialogCancel` before `AlertDialogAction` in the DOM.                                           | WAI-ARIA alertdialog |
| 4   | The removing button is labelled with a verb and an object, never "OK" or "Yes".                      | "Remove window"; the safe button says what it keeps: "Keep window".                                  | P10.1                |
| 5   | The dialog stays open until the server answered. The item disappears only after that.                | `Button loading` ("Removing…"); `onRemove` resolves with the API envelope.                           | P12.1                |
| 6   | A failure appears inside the dialog, in words, and the person can try again or cancel.               | Alert in the dialog: server message, or "The server did not answer" when offline.                    | P12.2                |
| 7   | A click outside does not dismiss the question.                                                       | `alertdialog` role; no outside-press close.                                                          | WAI-ARIA alertdialog |

## Code

```tsx
<AlertDialog open={target !== null} onOpenChange={(open) => !open && close()}>
  <AlertDialogContent>
    <AlertDialogHeader>
      <AlertDialogTitle>Remove Fri 13 Nov, 10:00 to 12:00?</AlertDialogTitle>
      <AlertDialogDescription>
        Mentees can no longer book this window.
      </AlertDialogDescription>
    </AlertDialogHeader>
    <AlertDialogFooter>
      <AlertDialogCancel>Keep window</AlertDialogCancel>
      <AlertDialogAction
        variant="destructive"
        loading={removing}
        loadingLabel="Removing…"
        onClick={confirm}
      >
        Remove window
      </AlertDialogAction>
    </AlertDialogFooter>
  </AlertDialogContent>
</AlertDialog>
```

## Known limits

- After the item is removed, where focus goes is the page's decision. Move it to the list heading, not to the page top.
- No undo exists. If the product adds one, this pattern is replaced by "do it and offer undo" for that object.
